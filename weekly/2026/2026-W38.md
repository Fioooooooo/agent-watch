# Agent / Harness 技术周报｜2026 W38

> 证据范围：以 2026-09-12 至 2026-09-18 已归档 daily 为主，并回查少量官方原文验证关键判断。9 月 12 日日报包含 V2.1 发现的前序漏报；其中 OpenAI Agents API、Cursor Projects、GitHub Copilot managed permissions、DeepSeek V4.1-Flash 的原始发布时间早于本周时间边界，本文只在需要说明架构趋势时引用，不把它们计作本周新发布。

## 本周判断

本周最重要的变化不是某个 Coding Agent 又增加了多少功能，而是 **Agent Harness 的状态模型开始明显分层**。

一方面，Claude Code Projects、Cognition Fusion、Qwen Code Agent Board 都在把“多 Agent”从同一会话内的临时分工，推进为多个独立执行上下文之间的长期协作；另一方面，Claude Code、Qwen Code、Kimi Code 持续补齐 resume、checkpoint、权限、hook、budget 与后台执行语义，说明 session 已经不再等同于 transcript，而是一个包含上下文、权限、工具连接、生命周期和执行位置的运行时实体。

与此同时，Gemini CLI 把不可信输入的 provenance 跨工具调用传播到后续授权判断，VS Code Agent Host 则开始让同一 Agent session 跨 frontend、workspace 和 execution environment 迁移。这两条变化共同说明 Harness 正在从“模型 + tool loop”演进为具有明确 **state scope、security state、execution state 与 portability** 的运行时系统。

本周没有出现足以单独改变 Harness 设计的新模型发布。模型侧最值得继续跟踪的仍是上周 DeepSeek V4.1-Flash 所代表的 KV cache / 长上下文成本优化，但它不属于本周新发布。

## 1. Harness：Session 正在从聊天记录变成可迁移的运行时实体

### 事实更新

**Claude Code 2.1.269～2.1.273** 在一周内连续修改长期会话的恢复与运行时语义：Workflow 并发上限可提高到 256；`/goal` 对 API 错误、网络中断和 token limit 增加退避重试与显式暂停；resume、compaction、prompt cache、后台 Agent、MCP reconnect、managed policy 等状态持续修复。2.1.271 又把 WebFetch 的网络授权下沉到 per-command 生命周期，并为 streaming input 增加显式 drain marker；2.1.273 开始向 LLM gateway 暴露 agent type、request class、前序工具耗时、compaction 状态等 Harness 元数据，并支持把 Remote Control session fork 为本机后台 session。

- 官方：<https://github.com/anthropics/claude-code/releases/tag/v2.1.269>
- 官方：<https://github.com/anthropics/claude-code/releases/tag/v2.1.271>
- 官方：<https://github.com/anthropics/claude-code/releases/tag/v2.1.273>

**Qwen Code 0.23.4** 把中断会话继续执行、checkpoint 诊断、HookSessionMeta、reasoning replay、workspace MCP 恢复与信任状态等能力汇入稳定版本。随后 0.24.0 又增加 background result execution tracking、hook progress events 和来自 extensions 的 dynamic workflows，说明 session lifecycle 与 workflow lifecycle 仍在继续显式化。

- 官方：<https://github.com/QwenLM/qwen-code/releases/tag/v0.23.4>
- 官方：<https://github.com/QwenLM/qwen-code/releases/tag/v0.24.0>

**Kimi Code 0.43.0** 调整 Goal Mode 的时间预算：会话关闭期间不再消耗 active time，并取消此前 24 小时上限。长期任务的预算开始按实际运行生命周期计算，而不是简单使用墙钟时间。

- 官方：<https://www.kimi.com/code/docs/en/kimi-code/whats-new.html>

**Visual Studio Code 1.138** 把 Agent Host 推进为独立 Harness 宿主层。Agent harness 运行在基于 AHP 的独立进程中；同一 Codex session 可以跨 ChatGPT app 与 VS Code 延续，workspace 可以后绑定，tool surface 可以由 VS Code / extensions / MCP 提供，execution environment 还可以迁入项目 Dev Container。

- 官方：<https://code.visualstudio.com/updates/v1_138>
- Agent Host 架构：<https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture>

### 趋势分析

这些更新放在一起后，session 的边界已经发生变化。过去 session 主要意味着“conversation history + 当前工作目录”；现在至少需要独立保存和恢复：

- conversation / compacted context；
- model 与 reasoning state；
- tool / MCP connection；
- permissions / trust / network policy；
- hooks 与 workflow lifecycle；
- background execution state；
- workspace binding；
- execution environment；
- frontend attachment；
- runtime budget 与 usage。

因此，**resume 的工程目标正在从“重新打开对话”变成“恢复一个语义等价的 Agent runtime”**。VS Code 的 AHP / Agent Host 又进一步证明，session identity 可以独立于具体客户端和执行环境存在。后续 Harness 架构里，Session Manager 会越来越接近独立基础设施层，而不是 Chat UI 的内部模块。

## 2. Multi-Agent：核心问题从“怎么调用子 Agent”转向“状态如何分层”

### 事实更新

**Cognition Fusion** 在 Devin Desktop 与 CLI 中采用 lead + sidekick 双 Agent 结构。两者不是在同一 transcript 中切换模型，而是各自维护独立持久上下文；lead 负责规划、歧义处理和最终审查，sidekick 负责探索、实现和测试，只交换任务简报、结果与反馈。Cognition 给出的直接工程原因之一是避免模型切换破坏 prompt cache。

- 官方：<https://cognition.com/blog/local-fusion>

**Qwen Code Agent Board** 在 nightly 中提供一个独立于模型上下文的共享工作状态层。多个独立启动的 Agent 可以通过本机持久化 board 创建任务、claim / done、note，以及带 TTL 的 ask / answer。Board 不负责启动、唤醒或调度 Agent，也不会自动执行其中的文本。

- 官方 Release：<https://github.com/QwenLM/qwen-code/releases/tag/v0.23.3-nightly.20260913.faa395885e>
- 设计文档：<https://github.com/QwenLM/qwen-code/blob/v0.23.3-nightly.20260913.faa395885e/docs/users/features/agent-board.md>

**Claude Code Projects** 在 9 月 17 日完成更明显的上层分层：Project 保存长期目标、环境、instructions、shared memory 与 library；coordinator 负责拆解、派发、审查和汇总；每个 thread 是独立 Claude Code cloud session，拥有自己的 branch 和 repo copy；thread 内还可以继续使用 subagents、loops 与 workflows。

- 官方：<https://claude.com/blog/projects-redesigned>

### 趋势分析

本周三个实现给出了不同层级的答案：

```text
Project / Goal scope
  ├─ shared memory / artifacts / constraints
  └─ Coordinator
       ├─ Session / Thread A
       │    └─ Subagent / Workflow
       ├─ Session / Thread B
       │    └─ Subagent / Workflow
       └─ Session / Thread C

Cross-session coordination surface
  └─ task / claim / done / ask / answer / result
```

这里最重要的变化是 **共享状态不再默认等于共享上下文**。Fusion 用任务简报隔离 lead 与 sidekick；Agent Board 把任务所有权和异步问答放到 transcript 之外；Claude Projects 把 shared memory 提升到 Project scope，而每个 thread 继续保有独立 session context。

这使 Multi-Agent 的设计问题从“如何让一个 Agent 调另一个 Agent”转向三个更稳定的问题：哪些状态属于 Project，哪些属于 Session，哪些只属于 Worker；哪些信息应该复制，哪些应该引用，哪些应该通过结构化 handoff 传递；谁拥有最终决策权和结果审查权。

## 3. Context Engineering：上下文开始被当成受预算约束的运行时资源

### 事实更新

Qwen Code 9 月 13 日 nightly 集中加入 Web Shell context overview、手动 `/compress`、compression ownership 检查、Computer Use compact observation、observation bound、减少模型往返，以及 shell output producer budget。压缩必须由当前 live session owner 执行，跨 session / pane 后不能把旧压缩结果写入新的 owner。

- 官方 Release：<https://github.com/QwenLM/qwen-code/releases/tag/v0.23.3-nightly.20260913.faa395885e>
- Context 设计：<https://github.com/QwenLM/qwen-code/blob/v0.23.3-nightly.20260913.faa395885e/docs/design/2026-09-12-web-shell-context-compaction.md>

OpenAI Agents API 虽然发布于 9 月 10 日、属于本周 V2.1 补录而不是本周新发布，但它提供了一个重要的对照：OpenAI 把自动 compaction、tool search、programmatic tool calling 和每个 subagent 独立 context 直接作为托管 Harness 能力，并明确强调保持模型 cache 的效率。

- 官方：<https://openai.com/index/introducing-the-agents-api/>

### 趋势分析

Context Engineering 正从 prompt 层面的“摘要技巧”下沉到运行时资源治理。需要治理的不只是 token 数量，还包括：谁有权触发 compaction、哪些 observation 可以进入 context、工具输出有多少预算、subagent 能看到哪些父上下文、压缩后的状态如何参与 cache 和 resume。

这与 Multi-Agent 的状态分层是同一个问题的两面：**上下文应该是某个 scope 的投影，而不是系统全部状态的副本。** Project memory、session context、worker brief、tool observation 和 runtime metadata 会继续分离，Harness 负责决定每次模型调用实际看到哪一层。

## 4. Runtime / Sandbox / Permissions：授权开始带来源、历史和因果链

### 事实更新

Gemini CLI 9 月 12 日 nightly 引入跨工具的 Prompt Injection 防护。来自 Web、MCP、外部文档等 `<untrusted_context>` 的内容如果影响 shell flags、文件编辑或构建配置，后续执行 `npm run`、`make`、`cargo` 等构建 / 测试命令会重新进入授权判断。与此同时，sandbox 开始更严格隔离宿主机持久配置、凭证、trusted folders、policy state、realpath / symlink 与 ephemeral runtime state。

- 官方 Release：<https://github.com/google-gemini/gemini-cli/releases>
- Prompt Injection PR：<https://github.com/google-gemini/gemini-cli/pull/29250>
- Sandbox PR：<https://github.com/google-gemini/gemini-cli/pull/29214>

Claude Code 本周也持续修复权限状态一致性，包括 per-command allowed domains、无法静态分析的 Bash 命令、subshell 隐藏危险命令、managed MCP / connector policy、resume 后权限行为等。

- 官方：<https://github.com/anthropics/claude-code/releases/tag/v2.1.271>
- 官方：<https://github.com/anthropics/claude-code/releases/tag/v2.1.273>

GitHub Copilot 9 月 9 日的 managed permissions 属于本周日报补录的前序事件，它让企业管理员集中规定 shell、文件和网络操作是 block、require confirmation 还是 auto-approve，并覆盖本地自动批准策略。

- 官方：<https://github.blog/changelog/2026-09-09-enterprise-managed-permissions-for-github-copilot-agent-operations/>

### 趋势分析

Agent permission model 正在从：

```text
Tool / Command -> allow | ask | deny
```

扩展为：

```text
Action
 + provenance of input
 + previous mutations
 + current trust state
 + execution environment
 + organization policy
 + side-effect class
 -> allow | ask | deny
```

Gemini CLI 的 build-file taint 最具有代表性，因为它明确让前序工具调用改变后续工具调用的授权结果。权限因此成为一个随 session 演进的安全状态机，而不是无状态过滤器。Sandbox 也不再只是“命令跑在容器里”，还需要隔离宿主机的信任决定、凭证和策略状态。

## 5. Harness 基础设施：托管层与宿主层同时成形

### 事实更新

OpenAI Agents API（9 月 10 日，本周补录）把 Codex 的 Harness 与长期运行基础设施开放成托管 API：OpenAI 维护 Harness，开发者可以选择 OpenAI sandbox、自有基础设施或第三方 sandbox；API 原生提供 durable session、context compaction、tool search、programmatic tool calling、MCP 和 multi-agent。

- 官方：<https://openai.com/index/introducing-the-agents-api/>

VS Code Agent Host 则从另一个方向提供宿主层：Harness 可以作为独立进程被客户端连接，同一 session 可以跨窗口、跨应用、跨 workspace 和 execution environment 延续。

- 官方：<https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture>
- 本周更新：<https://code.visualstudio.com/updates/v1_138>

### 趋势分析

这两个方向并不冲突。OpenAI 在把 **Harness as a managed runtime** 产品化，VS Code 在把 **Harness as a portable process** 产品化。两者都要求把模型、session、tool surface、sandbox 和 frontend 解耦。

后续值得关注的不是是否会出现一个统一 Agent 框架，而是这些边界是否逐渐形成可互换接口：session protocol、tool protocol、execution environment contract、authorization state、artifact / memory storage。MCP 已经覆盖工具接入的一部分，ACP / AHP 则分别在 Agent-client / Agent-host 关系上探索接口，但本周没有足够新的协议级变化支持更强判断。

## 接下来值得持续观察

1. **Project / Session / Worker 的状态边界是否继续标准化。** Claude Projects 已经给出 Project → Thread → Subagent 的产品级实现，Qwen Agent Board 则给出跨 session 协作原语。重点观察 shared memory 的写入规则、冲突处理、provenance 与自动更新策略。

2. **Session portability 是否从单产品能力变成协议能力。** VS Code AHP 已经让 Harness 独立于客户端；需要继续观察 session identity、permission state、workspace binding 与 execution environment 是否能够跨不同宿主可靠迁移。

3. **Permission 是否演进为完整的因果安全状态机。** Gemini CLI 已经开始跨工具传播不可信来源，下一步重点是 provenance 如何持久化、compaction 后是否保留、subagent handoff 是否继承，以及企业 policy 如何覆盖这些状态。

4. **长期任务的恢复正确性如何被测试。** Claude Code、Qwen Code、Kimi Code 都在补 resume / budget / background lifecycle，但当前主要仍靠逐项修复。值得观察是否出现针对“中断前后语义等价”的系统化 checkpoint schema、replay test 与 eval。

5. **Context budget 是否成为 Harness 的统一调度资源。** Qwen 已把 observation、compression、shell output 与 model round-trip 纳入预算；OpenAI Agents API 则把 compaction 与 tool search 托管化。下一步会涉及跨 Agent 的 token / cache / tool-result budget 分配，而不仅是单 session context window。

## 证据完整性说明

本周日报在启用 V2.1 后多次标记 `coverage incomplete`，主要原因不是已知来源确认无更新，而是部分官方入口无法持续取得“最新 3～5 条”的可验证序列。周报遵循 sources.md 的职责划分，没有重新执行一遍每日全量扫描，因此本文的趋势判断以已归档 Evidence 和少量官方回查为边界。
