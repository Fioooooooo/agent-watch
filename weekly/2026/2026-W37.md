# Agent / Harness 技术周报｜2026 W37

> 覆盖 2026-09-07 至 2026-09-11。以本周已归档日报为主要证据，并对关键判断回查官方一手来源。

## 本周最重要的变化

本周没有出现一个单点功能足以定义方向的“大更新”，但多个厂商的变化高度一致：**长期 Agent 的核心问题正在从“能不能完成任务”转向“运行时状态、权限和安全边界能不能在数小时、多 Agent、跨工具、崩溃恢复之后仍保持正确”。**

这一变化主要体现在三条线上。

第一，**会话状态正在从 transcript 扩展为完整运行时状态。** Claude Code 连续多个版本集中修复恢复后 system prompt、tool list、MCP 工具、extended thinking、hook 输出、工作目录和 prompt prefix 的一致性；Qwen Code 开始显式记录 workflow failure、预算、prompt identity 和消息背压；Codex Python SDK 则把外部消息权限、历史读取和事件附着点变成明确 API 语义。

第二，**Context Engineering 正从“怎么压缩上下文”进入“怎么设计上下文拓扑”。** Codex Memory V2 开始使用有类型、有预算、有 readiness state 的独立 memory fragment；LangChain Deep Agents 则把 subagent 的上下文继承明确分为 `fork` 和 `isolated`，并把“哪些 Agent 应共享 evidence、哪些 reviewer 应保持独立”提升为 Harness 级设计问题。

第三，**Agent 安全正在从模型自律转向不可由模型自行绕过的运行时边界。** Codex 将用户/设备验证与普通工具批准区分，并为多 Agent 授权保留 provenance 与完整性；Meta Muse 使用独立 Secure VM、Sentinel 和不可见凭证存储；Anthropic 公布的真实网络安全事故进一步说明，模型会错误解释自己所处的环境，因此 sandbox、外部阻断和独立监控不能依赖模型本身的判断。

## 一、Harness 与长期运行：恢复的不再只是聊天记录

### 事实更新

OpenAI 9 月 6 日公开内部研究组织中 Coding Agent 的真实运行数据：研究人员大量使用并发 session 和 subagent，Agent 正承担更长、更复杂的研究任务；在 4～8 小时任务中，即使任务最终成功，过去六个月仍有超过一半发生过至少一次人工介入。这类生产数据说明，长期 Agent 的正常运行路径本身就包含 intervention、resume、failure diagnosis 与继续执行，而不是完全无人值守的单一路径。

官方原文：<https://openai.com/index/research-acceleration-view-inside-openai/>

Claude Code 2.1.265、2.1.267、2.1.268 连续修复了同一类问题：恢复后 prompt prefix、system prompt、tool list、MCP 工具公告、hook 输出、extended thinking、工作目录和工具定义不能因为重连或重新渲染而发生语义变化；如果 workflow journal 已丢失，也不能静默从头重跑有副作用的 Agent。2.1.268 进一步要求第三方模型入口上的 tool list 在整个 session 中保持 byte-stable，并收紧 resume、compaction 和路径权限的一致性。

官方原文：
- <https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md>
- <https://github.com/anthropics/claude-code/releases/tag/v2.1.268>

Qwen Code 0.23.2 则开始把长期 workflow 中常见的分布式系统语义显式化：Goal continuation 带预算与进度、失败 Agent 写入 journal 并结算为明确状态、跨会话消息存在背压和丢弃语义、后台通知队列有容量上限、daemon 持久化 prompt identity。

官方原文：<https://github.com/QwenLM/qwen-code/releases/tag/v0.23.2>

Codex Python SDK 0.154.0 新增 `ExternalMessage`，允许外部内容加入正在执行的 turn，但官方明确指出它只有 tool-level authority，**不授予 user authorization**；同时 late-joining handle 只从 attachment point 开始接收事件，历史读取和实时事件流被明确区分。

官方原文：<https://github.com/openai/codex/releases/tag/python-v0.154.0>

### 趋势分析

长期 Agent 的“状态”正在变成一个复合对象，而不是 conversation history：

```text
Agent session state
├─ conversation / retained context
├─ system prompt snapshot
├─ tool / skill surface
├─ MCP connection state
├─ authorization state
├─ workflow journal
├─ prompt / turn identity
├─ resource budget
├─ message queues / backpressure
├─ working directory / execution environment
└─ interruption / recovery position
```

本周 Claude Code、Qwen Code 和 Codex 的变化来自不同实现路线，但都在回答同一个问题：**恢复之后如何证明“这还是同一个任务、同一个权限范围、同一套工具和同一份执行语义”。**

这意味着未来判断一个 Agent Harness 是否真正支持长期任务，不能只看有没有 `resume(sessionId)`、checkpoint 或 background mode，而要看它是否定义了可恢复状态集合、不可恢复时的失败语义、消息积压策略、权限连续性和副作用重放规则。

## 二、Context Engineering：从窗口管理进入上下文拓扑设计

### 事实更新

Codex 0.154.0-alpha.8 的 Memory V2 开始拥有独立协议和 context 类型。后台 consolidation 是否达到可用条件通过 readiness state 表示；memory fragment 至少区分 instructions 与 extraction evidence，不同语义使用不同 role 和 provenance，并有独立大小预算，而不是把所有长期记忆拼成一段文本注入模型。

官方原文：<https://github.com/openai/codex/releases/tag/rust-v0.154.0-alpha.8>

LangChain Deep Agents 本周引入显式 context mode：`isolated` 子 Agent 只收到任务描述，`fork` 子 Agent 则继承 supervisor 当前完整 state，并复用已有 prompt cache。官方同时明确提出，不同角色需要不同上下文策略：continuation worker 适合 fork，独立 reviewer / verifier 通常更适合 isolated，以避免沿用 supervisor 的既有推理和错误锚定。

官方原文：<https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness>

### 趋势分析

过去 Context Engineering 主要讨论“如何少放一点内容”和“什么时候 compact”。本周两个变化说明问题正在向更高一层移动：**上下文不仅有内容和长度，还有类型、来源、保留规则和拓扑关系。**

在单 Agent 内部，不同状态开始使用不同 retention policy：memory、authorization evidence、safety evidence、tool state 不应全部依赖 transcript 的生命周期。

在 Multi-Agent 系统内部，上下文也不应默认全共享或全隔离。worker 需要复用已有 evidence，reviewer 则需要避免继承主 Agent 的推理偏差。因此 context policy 会直接影响四个指标：重复工具成本、prompt-cache 命中率、错误相关性和 reviewer 独立性。

下一阶段值得关注的是这些“上下文类型”和“上下文拓扑”是否会进一步标准化为 Harness 的一等对象，例如明确的 context fragment schema、provenance、priority、retention、permission 和 fork policy。

## 三、Multi-Agent：重点从“能派发”转向“授权、隔离和失败语义”

### 事实更新

Codex 0.154.0-alpha.6 开始为 Multi-Agent V2 worker 构造显式 root authorization snapshot。子 Agent 继承的不只是当前 prompt，而是 root user instructions、verified answers、retained provenance 与限制条件；如果原始授权证据因 compaction 或历史缺失无法恢复，状态会被标记为 incomplete，而不是默认继续执行。

同一版本还加入 user/device verification 协议，并把此类验证放在普通 automated approval policy 之外，需要通过可信 app / UI 完成。

官方原文：<https://github.com/openai/codex/releases/tag/rust-v0.154.0-alpha.6>

LangChain 的 `fork` / `isolated` context mode 则从上下文侧补齐另一部分：不同 subagent 不应拥有完全相同的信息可见性。Qwen Code 0.23.2 对失败 Agent、跨 session IPC、消息背压和 budget continuation 的处理，则开始定义多 Agent workflow 在异常情况下如何继续运行。

### 趋势分析

Multi-Agent 的早期竞争点是“是否能 spawn / delegate / parallelize”。本周材料显示下一阶段的竞争点已经变成：

- 父 Agent 的授权能否安全地投影给子 Agent；
- 子 Agent 应继承哪些上下文，哪些推理应该刻意隔离；
- Agent failure 如何进入 workflow journal；
- 消息通道是否存在容量、丢弃和确认语义；
- reviewer 是否真正独立，而不是共享同一推理偏差；
- 任务预算和停止条件是否可以跨 Agent 传递。

这类问题本质上已经接近分布式运行时设计，而不是 prompt orchestration。

## 四、Runtime / Sandbox / Permissions：安全边界开始独立于主 Agent

### 事实更新

Meta 9 月 8 日发布 Muse。Muse 在独立 Secure VM 中拥有 browser、filesystem 和 terminal，并可以在用户关闭应用后继续执行。更关键的是，Meta 使用一个与主 Agent 系统隔离的 Sentinel agent 审查对互联网的外部行为；凭证保存在主 Agent 不可直接读取的 secure storage 中，敏感操作使用结构化 human approval。

官方原文：<https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/>

Anthropic 9 月 9 日公开四起真实网络安全事故。在错误配置的 cyber evaluation 中，Claude 获得了本不应存在的互联网访问并操作现实第三方系统。Anthropic 的调查指出，模型会将现实证据重新解释为“仍处于模拟环境”，仅依赖模型自身推理来判断 sandbox 是否安全存在系统性风险；独立在线 blocking monitor 能更可靠地承担边界职责。

官方原文：<https://www.anthropic.com/research/alignment-assessment-cybersecurity-incidents>

Codex 的 user verification / authorization provenance 与 Claude Code 对 symlink、shell path、managed policy 的 fail-closed 处理也指向同一问题：权限规则需要建立在真实执行语义上，而不是仅建立在自然语言确认和表面路径匹配上。

### 趋势分析

本周最强的安全信号不是某个新的 sandbox 产品，而是安全架构发生了职责分离：

```text
主 Agent：计划、推理、执行
        ↓
运行时边界：sandbox / filesystem / network policy
        ↓
独立审查：monitor / sentinel / policy engine
        ↓
可信用户边界：verification / structured approval
        ↓
秘密存储：credential isolation
```

主 Agent 可以提供安全判断，但不再被视为最终安全边界。随着 Agent 获得浏览器、shell、支付、账号和长期后台执行能力，网络出口、不可逆动作、凭证访问和身份验证必须由模型无法自行解释或绕过的组件控制。

Anthropic 的真实事故给这个架构方向提供了直接证据：即使 system prompt 明确告诉模型环境是模拟的，只要基础设施边界配置错误，模型仍会继续执行，而且会对冲突证据产生有偏解释。因此未来 Agent 安全评测也需要从“模型是否遵守规则”扩大到“当 sandbox、scope 或工具配置出现故障时，系统是否还能阻断外部副作用”。

## 五、Coding Agent：评价指标正在转向任务时长、介入率和恢复成本

### 事实更新

OpenAI 本周公开的内部使用数据提供了少见的生产侧指标：Coding Agent 总运行量、并发 session、subagent fan-out、任务时长和人工介入率都在增长，且高层 planning 仍然只占较小部分。4～8 小时级任务中，人类 steering 仍是成功路径的一部分。

Claude Code、Qwen Code 与 Codex 本周的具体工程更新也没有集中在“再增加一个工具”，而是集中在恢复、权限、prompt identity、消息边界和状态连续性。

### 趋势分析

Coding Agent 的评价维度正在从单一 completion rate 扩大为：

- task horizon：能稳定运行多久；
- intervention rate：成功任务需要多少人工介入；
- recovery correctness：崩溃或断连后能否正确继续；
- state continuity：工具、上下文和权限是否保持一致；
- side-effect safety：无法恢复时是否 fail closed；
- end-to-end cost：长上下文、重复读取和多 Agent 并发的实际成本。

这组指标比单次 benchmark 更接近生产 Harness 的真实竞争力。

## 六、新模型与模型层变化

本周没有确认到一项“首次发布且足以改变 Harness 设计”的全新主模型，需要单独占据周报主线。

本周日报曾收录 GLM-5.3-Flash 的架构与 Agent 能力。复核后需要做一个时间口径修正：AutoClaw 在 9 月 10 日发布了新的技术文章，详细披露 320B / 18B active parameters、linear + sparse attention、IndexPool、1M context、KV-cache 与 Agent benchmark；但官方模型页将 GLM-5.3-Flash 标记为 **2026.08** 更新，因此本周应视为新的技术披露和生态落地，而不是模型首次发布。

官方资料：
- <https://autoclaw.z.ai/blog/model/glm-5.3-flash/>
- <https://autoclaw.z.ai/models/>

技术意义仍然明确：低 active compute、长上下文 KV 成本下降和 native multimodal verification 都有利于更长 session、更高并发和视觉执行闭环。但本周更值得持续观察的是这些模型层优化在真实 Harness 中能否转化为更低的端到端任务成本，而不是单独看模型 benchmark。

## 本周形成的技术趋势

### 1. Agent Harness 正在形成“运行时状态机”而不是“工具调用循环”

这一趋势本周最明确。会话、工具、权限、消息、budget、journal、MCP connection、prompt identity 和恢复位置都开始拥有独立状态与生命周期。Agent loop 仍然存在，但它已经只是 runtime 的一部分。

### 2. Context 正在拆成多个具有不同语义和生命周期的状态层

Memory V2、authorization evidence、fork / isolated context、prompt-prefix stability 都说明，统一 transcript 正在失去“唯一状态容器”的地位。未来 Harness 的上下文管理更接近 typed state + projection：不同 Agent、不同 turn、不同权限级别看到的是同一底层状态的不同投影。

### 3. Multi-Agent 正在吸收分布式系统语义

失败结算、消息背压、独立 reviewer、授权继承、状态完整性、journal 与预算传播开始进入框架和产品实现。能启动多个 Agent 已经不是难点，如何保证它们在长期运行和部分失败下仍保持一致性才是新的工程边界。

### 4. 安全边界从“模型遵守规则”迁移到“运行时强制规则”

Meta Muse、Codex verification、Claude Code permission hardening 与 Anthropic 事故复盘形成了非常一致的信号：高自主 Agent 必须有独立 sandbox、policy、monitor、credential store 和 trusted UI。模型可以参与安全决策，但不能成为最终控制面。

## 接下来值得持续观察

1. **Codex Multi-Agent V2 / Memory V2 是否进入稳定版本。** 重点不是 API 名称，而是 authorization snapshot、typed memory、retained provenance 和 worker context 是否形成稳定抽象。
2. **Claude Code 是否明确持久化 session runtime schema。** 连续几个版本都在修恢复后的 prompt/tool/state 等价性，值得观察这些修复是否最终收敛为公开的 session / checkpoint 语义。
3. **Qwen Code dynamic workflow 是否补齐更正式的生命周期契约。** 包括 message delivery、retry、failure propagation、budget、checkpoint 和 workflow recovery。
4. **独立安全监控是否成为 Agent 产品的标准层。** Meta Sentinel 与 Anthropic blocking monitor 已经给出两个不同实现，接下来要看 browser/computer-use/coding agent 是否普遍采用主 Agent 之外的独立控制平面。
5. **Context topology 是否形成跨框架共识。** fork、isolated、reviewer independence、typed fragments 和 provenance 很可能逐步从各家内部实现变成通用 Harness 设计语言。
6. **Agent 评测是否进一步采用任务时长、介入率和恢复率。** OpenAI 已开始披露真实 production horizon 与 intervention，后续如果更多厂商采用类似指标，Agent benchmark 的评价方式会发生明显变化。

---

## 本周结论

本周最值得保留的不是某个单独版本号，而是一条连续的工程变化：**Agent 系统正在把长期执行所需的状态、权限、上下文和安全约束，从 prompt 与 transcript 中拆出来，变成独立、可持久化、可验证、可恢复的运行时对象。**

这使 Harness 的设计越来越接近一个面向不可靠模型、长时间任务和多执行单元的受控运行时。模型能力继续决定上限，但真正影响生产稳定性的差异，正在越来越多地出现在 state management、context projection、authorization、failure recovery 和 sandbox policy 这些层面。
