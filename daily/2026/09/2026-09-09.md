## Meta / Muse — Personal Agent 采用 Secure VM + Sentinel 的双层执行与安全架构

- **Source:** Meta / Muse
- **Published:** 2026-09-08
- **Topics:** Agent Runtime, Sandbox, Security, Long-running Agents, Browser Use, Permissions, Memory
- **Priority:** ★★★★★
- **Original:** <https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/>
- **Design:** <https://introducing.muse.ai/>

### What changed

Meta 正式发布个人 AI Agent Muse。与普通聊天助手不同，Muse 在独立的 **Muse Secure VM** 中运行，拥有自己的浏览器、文件系统与 terminal，可以跨应用完成任务，并在应用关闭后继续后台执行。

更重要的是，Meta 没有把安全完全交给主 Agent 自身：同一台机器上运行一个与 Muse 在系统层隔离的 **Sentinel agent**。官方描述是，Muse 发往互联网的行为需要经过 Sentinel 审查；当动作需要用户许可时，系统会显式请求批准。

Meta 还将凭证与 Agent 视野拆开：密码和支付方式进入 secure storage，Muse 可以使用凭证完成动作，但不能直接看到原始秘密。发送邮件、购物等敏感操作默认需要 human approval，并提供完整 activity / audit trail。

### Technical details

Muse 的执行结构已经接近一个完整的个人 Agent runtime：

```text
User goal / ongoing task
        ↓
       Muse
        ↓
Muse Secure VM
├─ browser
├─ filesystem
├─ terminal / generated code
├─ memory
├─ background scheduled / event-driven work
└─ connected apps
        ↓
   Sentinel agent
        ↓
network / sensitive action boundary
        ↓
user approval when required
```

官方设计文章进一步说明，Muse 不是 turn-by-turn agent：用户可以在上一项任务未完成时继续打断或追加任务；Agent 可以同时维护多个长期任务，并按 schedule 或 relevant event 主动继续工作。背景任务完成后，它会判断结果是否值得打扰用户，再决定是否发送通知。

在权限设计上，Meta 明确把部分控制做成 deterministic UI，而不是自然语言确认：关键动作使用结构化 accept / reject approval card，credential storage 也不暴露给模型。默认允许一般网页浏览，但对难以撤销的动作停止并请求人工确认。

### Why it matters

Muse 把“个人 Agent 的安全边界”从单一 sandbox 提升为多层 runtime policy：主 Agent 负责计划和执行，Secure VM 提供隔离执行环境，Sentinel 作为独立审查面控制外部效果，credential store 则把秘密从模型上下文彻底分离。

这与近期 Coding Agent 中出现的 permission state、trusted UI、MCP verification、approval provenance 属于同一个方向：高自主 Agent 不能只依赖 prompt 中的“不要做危险操作”，而需要由 Agent 无法自行绕过的执行平面约束 irreversible action、network egress、secret access 与 human approval。

**Worth reading:** 是。尤其值得关注做 browser/computer-use agent、personal agent、sandbox、credential isolation 和 long-running runtime 的实现者。

## OpenAI / Codex — 0.154.0-alpha.8：Memory V2 成为 Typed、Bounded Runtime Context

- **Source:** OpenAI / Codex
- **Published:** 2026-09-09 07:15 CST（GitHub 2026-09-08 23:15 UTC）
- **Topics:** Context Engineering, Memory, Agent Runtime, Long-running Agents
- **Priority:** ★★★★★
- **Original:** <https://github.com/openai/codex/releases/tag/rust-v0.154.0-alpha.8>
- **Status:** Pre-release / experimental

### What changed

Codex 0.154.0-alpha.8 的 tagged source 新增了明确的 Memory V2 protocol 与 model-context 类型，而不再只把 memory 当作普通文本注入。

App Server Protocol 新增 `MemoryStatusParams` / `MemoryStatusResponse`，用于判断后台 consolidation 是否已经积累足够的独立 thread，可以切换到 V2 memory context。默认 readiness threshold 是 20 个 consolidated threads，并显式返回 `v2_consolidated_threads` 与 `v2_ready`。

Core context 新增 `MemoryContextFragment`，目前至少区分两种语义：

- `ReadInstructions` → developer role / `memories.instructions`
- `ExtractionEvidence` → user role / `memories.extraction_evidence`

二者要求作为独立 message 进入 context，并进行明确的 size bound；当前实现将 fragment body 截断到约 8.9 KB，而不是允许 memory 无限侵占主模型窗口。

相关源码：

- Memory readiness protocol: <https://github.com/openai/codex/blob/rust-v0.154.0-alpha.8/codex-rs/app-server-protocol/src/protocol/v2/memory.rs>
- Typed memory context: <https://github.com/openai/codex/blob/rust-v0.154.0-alpha.8/codex-rs/core/src/context/memory.rs>

### Technical details

从 alpha.8 的 source delta 看，Memory V2 同时涉及 background consolidation、read path、write path、runtime readiness 与 typed context injection。这里的关键不是“加入长期记忆”本身，而是 memory 开始拥有自己的生命周期和上下文语义：

```text
historical threads
      ↓
background extraction / consolidation
      ↓
readiness state
      ↓
typed memory fragments
├─ instructions
└─ extraction evidence
      ↓
bounded model context
```

这与近期 Codex 对 Guardian evidence、authorization evidence、retained context 的处理方式一致：不同类型的长期状态不再全部压进统一 transcript，而是以独立 provenance、role、retention 和 truncation policy 进入模型上下文。

### Why it matters

对于 long-running Coding Agent，memory 的核心问题不是“是否保存信息”，而是何时写、何时读、读入哪些语义、占多少 context、是否已经有足够 evidence 可以切换策略。Codex 正在把这些问题显式放进 runtime 和 protocol，而不是仅靠 prompt 约定。

Memory V2 仍属于 alpha pre-release，接口与阈值都可能继续调整，但从实现形态看，**memory 正从文本附件演进为有类型、有预算、有 readiness state 的 context subsystem**。

**Worth reading:** 是。尤其适合关注 Agent memory、context provenance、background consolidation 与长任务状态管理的人。

## LangChain / Deep Agents — Forked Subagents：Context Mode 成为 Multi-Agent Orchestration Primitive

- **Source:** LangChain / Deep Agents
- **Published:** 2026-09-08
- **Topics:** Multi-Agent, Context Engineering, Prompt Caching, Agent Harness
- **Priority:** ★★★★★
- **Original:** <https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness>

### What changed

Deep Agents 为 subagent 新增显式 `context mode`，目前支持：

- `isolated`：子 Agent 使用全新的 context，只接收 supervisor 给出的 task description；
- `fork`：子 Agent 继承 supervisor 当前完整 state / conversation，再在此基础上执行新的 task。

Fork 模式不是简单复制文本。Supervisor 的 trailing tool call 会被移除，task description 被重写成新的 user message，并加入固定 preamble；子 Agent 完成后，supervisor 只接收最终结果作为原始 tool call 的 response。

LangChain 还明确让 fork 保留 prompt caching，因此当 supervisor 已经完成大量文件读取、错误定位或上下文收集时，worker 可以直接继承这些 evidence，而不需要重新调用工具收集一遍。

### Technical details

这篇文章把 subagent 的 context policy 与角色绑定：

```text
Supervisor
   ├─ worker / continuation → fork
   │      inherit evidence + prompt cache
   │
   ├─ verifier / reviewer → isolated
   │      avoid anchoring on supervisor reasoning
   │
   ├─ researcher → usually isolated
   │      keep question-specific context small
   │
   └─ memory agent → fork
          conversation itself is the evidence
```

这里最重要的设计判断是 reviewer 不应默认继承 supervisor 的推理过程。对于需要独立判断的 verifier，context isolation 不只是 token optimization，而是减少 anchoring / correlated failure 的治理手段。

Deep Agents 还展示了对 memory subagent 单独施加 filesystem permission restriction，使 context mode、tool surface、middleware 与 permission scope 可以共同定义一个 subagent 的 specialization。

### Why it matters

Multi-Agent 系统过去常把“子 Agent 看到什么”藏在 orchestration prompt 或框架默认行为里。Deep Agents 现在把它提升成显式 Harness primitive。

这使 context engineering 从“压缩主 Agent 上下文”进一步变成 **context topology design**：哪些 Agent 应共享历史，哪些必须保持独立，哪些 evidence 可以 fork，哪些 reasoning 应故意隔离。它同时影响成本、prompt cache 命中率、重复工具调用、review independence 和错误相关性。

**Worth reading:** 是。对 multi-agent coding、review agent、context engineering 和 prompt-cache optimization 都有直接参考价值。

## Anthropic / Claude Code — 2.1.265：Subagent Resume、Prompt Cache 与 Workflow Recovery 收敛到长期运行正确性

- **Source:** Anthropic / Claude Code
- **Published:** 2026-09-08（官方 changelog 不标具体时分）
- **Topics:** Coding Agent, Recovery, Multi-Agent, Prompt Caching, Sandbox, MCP
- **Priority:** ★★★★☆
- **Original:** <https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md>

### What changed

Claude Code 2.1.265 没有引入单一大功能，但集中修复了一组直接影响 long-running / multi-agent Harness 正确性的状态问题：

1. foreground-spawned subagent resume 后不再改变 tool list 与 system prompt prefix，避免恢复后 prompt-cache 失效；
2. agent teammates 与 resumed subagents 不再在后续 turn 把 `SubagentStart` hook context 和 preloaded skills 从 prompt prefix 中移走，保证请求前缀稳定；
3. 如果上一次进程在 tool 正在执行时死亡，resume 不再重写最后一个 prompt，而是保留该 tool call 并显式标记为 interrupted；
4. workflow container restart 后如果 run journal 丢失，系统会明确失败，而不是重新执行所有 agents；
5. background session 不再因为消息恰好到达 idle-timeout 边界而被中途 retire；
6. 修复 plugin path 中反斜杠绕过 symlink containment check 的问题；
7. non-interactive / Agent SDK / cloud session 中 `cd` 的工作目录现在可以跨 turn 保持；
8. MCP HTTP server 如果只支持旧版 HTTP+SSE transport，会按规范 fallback 到 SSE。

### Technical details

这些变化共同处理的是“恢复之后必须保持什么不变”：

```text
running session
   ↓ crash / background / resume / reconnect
restored session
   ├─ same prompt prefix
   ├─ same tool + skill surface
   ├─ interrupted tool state preserved
   ├─ shell cwd preserved
   └─ missing journal => explicit failure
```

Prompt-cache 在这里已经不是单纯成本优化。对于 subagent，system prompt、tool list、hook context 和 preloaded skills 的位置变化会同时影响 cache reuse 和恢复后的行为一致性。因此 Anthropic 正在把“可恢复状态”扩展到完整 execution context，而不是只恢复 conversation transcript。

### Why it matters

长期 Coding Agent 的失败往往发生在 turn 边界之外：进程退出、container restart、background timeout、Remote Control reconnect、subagent resume。2.1.265 的价值在于继续把这些异常路径变成显式、可恢复或 fail-closed 的生命周期状态。

其中 workflow journal 丢失后拒绝“从头重跑所有 agents”尤其重要：在有副作用的 Agent workflow 里，无法证明状态连续性时显式失败，比静默 replay 更安全。

**Worth reading:** 是。更适合关注 Coding Agent runtime、resume semantics、prompt caching 与 failure recovery 的实现者，而不是普通功能用户。

## Daily signal

今天四条更新实际上指向同一类架构变化：**Agent 的“状态”正在被拆分。** Conversation transcript 不再承担所有职责；memory 有独立 readiness 与 typed context，subagent 有独立 context topology，resume 有独立 execution state，安全则由 VM、Sentinel、credential store 与 deterministic approval boundary 承担。

当 Agent 进入长期运行、多任务并发、跨应用执行和多 Agent 协作后，Harness 的核心问题逐渐从“如何多调用几次模型”转为：哪些状态应该共享、哪些必须隔离、哪些能恢复、哪些必须由可信外部系统证明，以及哪些副作用在无法证明状态连续性时必须 fail closed。
