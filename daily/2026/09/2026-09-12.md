## 完整材料

### 1. Cognition：Fusion 进入 Devin Desktop 与 CLI，多模型协作从路由升级为双 Agent Harness

- **来源：** Cognition / Devin
- **发布时间：** 2026-09-11
- **主题：** Coding Agent、Harness、Multi-Agent、Context Engineering、Cost
- **优先级：** ★★★★★
- **原文：** <https://cognition.com/blog/local-fusion>

#### 发生了什么

Cognition 将 Fusion 正式带到 Devin Desktop 与 CLI。用户不再只选择一个模型，而是选择两个角色：

- lead：使用高能力模型，负责规划、处理歧义、控制会话与最终审查；
- sidekick：使用更具成本效率的模型，负责代码探索、实现、测试和结果回传。

官方强调 Fusion 不是简单的“根据任务难度切模型”。两个 Agent 并行运行，各自拥有独立、持续的上下文和工具；lead 向 sidekick 发送任务简报、约束和成功条件，sidekick 返回结果与反馈。两者不需要共享完整会话历史。

Cognition 给出的一个直接工程动机是：在同一任务内频繁切模型会破坏 prompt cache，导致所谓的便宜路由反而增加高价模型的重新输入成本。Fusion 通过独立持久上下文规避这一问题。

#### 技术细节

Fusion 的结构可以抽象为：

```text
User
  ↓
Lead Agent（高能力模型）
  ├─ 持久上下文 A
  ├─ 计划 / 歧义处理 / 审查
  └─ delegate(task brief, constraints, success criteria)
               ↓
        Sidekick Agent（执行模型）
          ├─ 持久上下文 B
          ├─ 探索代码
          ├─ 实现
          └─ 测试
               ↓
         result / feedback
               ↓
        Lead review / takeover
```

lead 始终保留最终控制权；sidekick 超出能力范围时，lead 可以接管。官方评测也开始以“每个任务成本”而不是“每 token 价格”衡量模型与 Harness 组合。

#### 为什么重要

这提供了一个比通用 model router 更稳定的多模型结构：角色边界、上下文边界和审查责任都是固定的，而不是每一步临时决定由哪个模型继续同一份 transcript。

它与最近 LangChain 的 `fork / isolated` 上下文模式、Codex 的子 Agent 授权快照、Qwen 的 workflow journal 都指向同一个问题：多 Agent 系统真正需要设计的是角色之间共享什么状态、谁拥有最终决策权，以及如何避免不同 Agent 的上下文互相污染。

**是否值得阅读全文：** 是。

### 2. Claude Code 2.1.269：Workflow 并发提升到 256，长任务恢复继续成为显式运行时语义

- **来源：** Anthropic / Claude Code
- **发布时间：** 2026-09-12 03:17（北京时间；官方 Release 2026-09-11 19:17 UTC）
- **主题：** Multi-Agent、Recovery、Context Engineering、Permissions、MCP、Long-running Agents
- **优先级：** ★★★★★
- **原文：** <https://github.com/anthropics/claude-code/releases/tag/v2.1.269>
- **Changelog：** <https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md>

#### 发生了什么

2.1.269 同时推进多 Agent 并发和长期任务恢复：

- 新增 `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`，单次 Workflow 可配置 1～256 个并发 Agent；
- `/goal` 遇到 API 错误、网络中断或 token limit 时不再静默卡死，而是退避重试，或暂停并明确说明原因，包括等待 usage limit 重置；
- response 因 output-token limit 被截断并自动续写后，修复下一轮 prompt cache 被部分失效的问题；
- 中途打断 Claude 后再 resume，不再改变旧上下文的重发方式而破坏 prompt cache；
- resumed headless session 在模型切换或请求重试发生于 turn 中间时，不再丢失该 turn 的回复；
- cloud session 首次请求会等待服务端配置，以减少 prompt cache miss；
- synced plugin MCP server 在远程 session resume 后恢复连接；
- compaction 后提供给 Claude 的 git status 改为当前状态，而不是 session 初始状态；
- 后台 Agent 仍在运行时，remote / headless session 不再错误报告“等待用户输入”；
- 修复路径级 deny rule、`tee` 写文件和 managed settings 等权限边界问题。

#### 为什么重要

这不是单一功能更新，而是继续把“恢复后的会话是否与中断前语义等价”做成可验证的运行时约束。并发 Agent 数量提升到 256 后，恢复、消息状态、MCP 连接和权限规则的不一致成本会进一步放大，因此扩展并发与强化恢复实际上是同一个 Harness 问题的两面。

**是否值得阅读全文：** 是，重点看 Workflow 并发、`/goal` 恢复、resume / cache 和后台 Agent 状态。

### 3. OpenAI Agents API：Codex Harness 与长期 Agent 基础设施正式成为托管 API

- **来源：** OpenAI
- **原发布时间：** 2026-09-10
- **主题：** Agent Harness、Long-running Agents、Sandbox、Multi-Agent、API
- **优先级：** ★★★★★
- **原文：** <https://openai.com/index/introducing-the-agents-api/>
- **状态：** 前序漏报补录

OpenAI 发布 Agents API 公测，把 Codex 使用的 Harness 与基础设施直接开放给开发者。官方明确把生产级 Agent 的关键能力拆成：上下文管理、工具效率、子 Agent 协调、可以持续运行数天的基础设施，以及能够保存文件和中间结果的执行环境。

开发者可以选择 OpenAI 托管 sandbox、自有基础设施或第三方 sandbox；Harness 由 OpenAI 托管维护，而其核心建立在开源 Codex Harness 上。官方还明确强调 durable session、recovery、multi-step execution、异步 fan-out 与 subagent orchestration。

这比普通 Agent SDK 更接近“托管 Agent runtime”：模型调用、上下文、工具编排、长期 session 与执行环境之间开始形成明确分层。

**是否值得阅读全文：** 是，本次补录中优先级最高。

### 4. DeepSeek V4.1-Flash：把 Agent 成本优化推进到模型架构与 KV cache 层

- **来源：** DeepSeek
- **原发布时间：** 2026-09-10
- **主题：** Model、Agent Cost、Long Context、Inference Efficiency
- **优先级：** ★★★★★
- **原文：** <https://www.deepseek.com/en/news/deepseek-v4-1-flash/>
- **状态：** 前序漏报补录

DeepSeek V4.1-Flash 使用 552B 参数 MoE，但输入阶段仅激活 8B、输出阶段激活 16B，并采用新的 Causal Encoder–Decoder 架构。官方给出的 KV cache 成本变化更值得 Agent 方向关注：相较上一代，HBM 占用降到 1/4，SSD 存储降到 1/8。

DeepSeek 特别指出 cache-hit 费用往往构成 Agent 总成本的重要部分，因此 KV cache 压缩不是普通推理优化，而会直接影响长上下文、多轮工具调用与长期任务的端到端成本。模型已经进入 DeepSeek API，并获得 CodeBuddy 与 OpenCode 支持。

**是否值得阅读全文：** 是，重点看非对称激活结构与 KV cache。

### 5. Cursor Projects：项目成为跨月持久上下文与大规模子 Agent 的上层运行单元

- **来源：** Cursor
- **原发布时间：** 2026-09-10
- **主题：** Multi-Agent、Persistent Context、Cloud Agent、Long-running Agents
- **优先级：** ★★★★★
- **原文：** <https://cursor.com/changelog/projects>
- **状态：** 前序漏报补录

Cursor Projects 面向 feature、migration、完整应用等长期工作，官方明确表示 Project 可以跨月维护上下文、向数千个 subagent 派发任务，并在没有新 prompt 时执行 recurring work。

Project 中的 coordinator agent 不直接写代码，而是负责规划、创建和管理执行 Agent，再把结果带回给用户检查。Project 运行在独立云端机器上，本地需要测试时再拉起 local agent。项目文件与共享上下文会同步到 cloud / local Agent 所使用的机器。

这意味着 Cursor 的上层抽象从“一个聊天 / 一个任务”继续向“持久项目运行时”移动，Project 开始承担任务分解、长期上下文和异构执行环境协调。

**是否值得阅读全文：** 是。

### 6. GitHub Copilot：企业级 Agent 权限开始由中央策略覆盖本地自动批准

- **来源：** GitHub Copilot
- **原发布时间：** 2026-09-09
- **主题：** Permissions、Agent Runtime、Enterprise Governance、Sandbox
- **优先级：** ★★★★☆
- **原文：** <https://github.blog/changelog/2026-09-09-enterprise-managed-permissions-for-github-copilot-agent-operations/>
- **状态：** 前序漏报补录

GitHub Copilot Business / Enterprise 管理员现在可以集中规定哪些 Agent 操作被阻止、哪些必须人工确认、哪些可以自动执行，覆盖 shell command、文件读写和网络域名。

关键点是 managed restrictions 不能被用户设置、workspace 设置、auto-approval 或此前保存的 approval 弱化，并且可以针对不同企业团队定义不同策略。能力适用于 Copilot app、Copilot CLI 与使用 Agent Host 的 VS Code session。

这与 Claude Code managed settings、Codex 用户验证和 Meta Sentinel 属于同一方向：高权限 Agent 的最终策略越来越由模型外的运行时 / 管理平面控制。

**是否值得阅读全文：** 值得快速阅读。
