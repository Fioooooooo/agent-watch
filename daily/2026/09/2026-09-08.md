### What changed

Codex 0.154.0-alpha.6 没有提供面向用户的完整 release notes，但 tagged source 中出现了一组高度相关的 runtime 变化：

1. App Server Protocol 新增 experimental `user-verification` API，将本地验证能力定义为独立协议面，包含 `status`、`enroll`、`delete`、`verify` 等操作；验证结果不是普通布尔确认，而是对 challenge 产生带 `credential_id` 的签名 proof。
2. MCP elicitation 增加专门的 user-verification routing。源码明确说明，这类 device verification 直接路由给 app，位于 automated approval policy 之外；当 UI 通道不可用或 policy 为 auto-deny 时，请求直接取消。
3. MultiAgent V2 的 worker authorization 开始显式从 root thread 构造授权证据快照。它不仅截取当前 prompt window，而是结合 retained context、verified answers、原始 user instructions 与 provenance 来判断授权是否完整；当根指令或验证答案缺失时，会把授权状态标记为 incomplete，而不是默认为可继承。

### Technical details

User Verification API 把“批准工具调用”和“证明当前操作者确实完成了可信验证”分成不同层级。协议中的 proof 包含 credential identifier，以及对精确 challenge 的 P-256 / SHA-256 ECDSA signature；同时定义 CredentialMissing、BiometricsUnavailable、ProviderUnavailable、UserCancelled、Timeout、AuthenticationFailed 等封闭错误状态。

运行时路径开始接近：

```text
Agent / MCP action
      ↓
authorization or verification requirement
      ↓
normal automated approval policy ──→ ordinary tool approval
      │
      └─ user/device verification required
               ↓
        trusted app / UI boundary
               ↓
        local verification provider
               ↓
           signed proof
               ↓
        resume privileged action
```

这意味着 verification 不再只是模型向用户问一句“是否允许”，而是可以成为 Harness 中不能被 Agent 自行代理通过的可信边界。

Multi-Agent 部分则处理另一类问题：root agent 已获得的授权，在 worker / subagent 中究竟如何继承。`root_user_authorization` 会为 MultiAgent V2 worker 投影 bounded root evidence，并区分 retained context 是否完整。源码明确规定 optional assistant context 不能挤掉 required grants or restrictions；如果历史 compaction 或旧记录导致原始 root instruction 无法恢复，则 authorization completeness 会被降级，并显式加入 `IncompleteRootInstructions` / `IncompleteVerifiedAnswers` 标记。

因此这里已经不是简单的“把父 Agent prompt 复制给子 Agent”，而是：

```text
root user instructions
+ verified answers
+ retained provenance
+ trusted skill scope
        ↓
authorization snapshot
        ↓
worker / reviewer
        ↓
complete / incomplete authorization state
```

### Why it matters

Agent 权限模型正在从一次性的 `allow / deny tool call` 扩展为多层 runtime authorization：普通 policy 可以自动决策一部分动作，但身份确认、设备验证或其他敏感动作需要穿过 trusted UI boundary；与此同时，多 Agent 系统不能仅依赖当前 context window 继承权限，而需要保留授权来源、完整性和限制条件。

这对 long-running / multi-agent Coding Agent 很关键。任务持续数小时、发生 compaction、resume、subagent fan-out 后，系统仍需要回答三个问题：谁授权了什么、这份授权是否仍完整、哪些动作必须重新由真实用户完成验证。Codex 这组 experimental changes 正在把这些问题从 prompt convention 下沉到 protocol、retained context 和 runtime state。

**Worth reading:** 是。尤其值得关注做 Agent permission、MCP、multi-agent delegation、trusted UI 或长期 session 的实现者。当前仍是 alpha pre-release，接口与语义可能继续调整，因此应把它视为明确的架构方向信号，而不是稳定 API 承诺。
