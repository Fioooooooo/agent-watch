# Agent 一手情报｜2026-09-06

本轮筛选出 2 条值得归档的新增信息。Qwen Code 继续把 dynamic workflow 从后台执行机制推进成具备可视化、控制、历史和跨 session 回执语义的一等 runtime surface；Gemini CLI nightly 则继续收紧 extension、workspace path 与系统级配置的信任边界。

## Qwen Code — 0.23.1-preview.0

- **Source:** Qwen / Qwen Code
- **Published:** 2026-09-05
- **Topics:** Workflow Orchestration, Multi-Agent, Session Runtime, IPC, Recovery
- **Priority:** ★★★★★
- **Original:** <https://github.com/QwenLM/qwen-code/releases/tag/v0.23.1-preview.0>

### What changed

Qwen Code 0.23.1-preview.0 延续 0.23.0 对多 Session Agent runtime 的建设，但重点从底层 workflow 能力推进到可观察、可控制和有明确消息终态的运行时表面：

- Web Shell 新增 capability-gated Workflow 体验，可浏览 saved workflows、live runs 和 history；
- 可以查看 phase、dispatch dependency、approval、logs 与 token usage；
- daemon 暴露能力时，可直接 pause、resume、cancel、retry、rerun 和 delete history；
- 新增 saved workflow 读取接口，展示 meta、阶段、脚本路径、最近运行和源码；未受信任 workspace 对未知或不可信 workflow fail closed，不暴露脚本；
- cross-session IPC 增加明确的 `refused` 回执，并为 held message 增加可配置 expiry，避免 sender 永久停留在不确定状态；
- session resource catalog 与 workflow projection 继续补齐 daemon / Web Shell 的 session 级 runtime state。

### Technical details

这次更新值得关注的不是 UI 本身，而是 dynamic workflow 正形成完整的 runtime contract：

```text
saved workflow definition
        ↓
workflow run
        ↓
phase / dispatch / approval / token state
        ↓
pause | resume | cancel | retry | rerun
        ↓
history + session projection
```

Workflow Web Shell PR 明确要求旧 task caller 保持兼容，同时通过 capability snapshot 显式启用新能力。对于未受信任 workspace，saved workflow 读取返回 unavailable，而不是泄露脚本内容。

跨 session messaging 的状态机也更明确。之前 policy-level refusal 会被错误表示成 `denied`，容易让发送 Agent 误认为有人主动拒绝；现在新增 `refused` 终态。被 hold 的消息默认五分钟后过期，也支持 1m、5m、10m 或 never，并且 `/peers` 显示剩余时间。实现上只为最早过期消息维护一个 timer，并在入口处额外 sweep overdue entry，避免休眠恢复后投递过期消息。

这使发送方能够区分 delivered / denied / refused / expired 等不同结果，并在已知窗口内获得终态，而不是让模型持续推理一条永远没有结果的跨 Session 消息。

### Why it matters

Qwen Code 正把 multi-agent / multi-session 协作从“多个 Agent 能互相发送消息”推进到具有 workflow graph、control plane、history、resource catalog 和 message-state semantics 的 runtime。

对于长期 Agent，可靠性不只来自任务 checkpoint。workflow 的 phase、dispatch、approval、token usage、pause/resume 状态，以及 Agent 间消息到底被拒收、人工拒绝还是超时，都需要进入持久、可查询的 runtime state。0.23.1-preview.0 在这条线上继续补齐控制面和可观测性。

**Worth reading:** 是。优先看 dynamic Workflow Web Shell、cross-session IPC receipt / expiry 和 session resource catalog。当前仍是 preview。

## Google — Gemini CLI 0.60.0 nightly (2026-09-05)

- **Source:** Google / Gemini CLI
- **Published:** 2026-09-05
- **Topics:** Sandbox, Permissions, Extension Security, Workspace Trust, Configuration Security
- **Priority:** ★★★★☆
- **Original:** <https://github.com/google-gemini/gemini-cli/releases/tag/v0.60.0-nightly.20260905.g85aca163f>

### What changed

Gemini CLI 0.60.0 的 9 月 5 日 nightly 继续围绕本地执行与 extension trust boundary 做安全加固：

- extension 修改环境变量时增加明确 consent；
- 对会改变 runtime 行为的环境变量进行 sanitize；
- command safety 和 file discovery 加强 workspace path boundary 与 symlink resolution；
- system-wide configuration path 强制更严格的 permission 与 ownership 检查。

该版本仍是 nightly pre-release。

### Technical details

前一轮 Gemini CLI 已经连续加固 MCP OAuth issuer、Seatbelt 临时目录与 extension path。此次进一步向“配置与运行环境本身”扩展：

```text
extension / config
      ↓
environment mutation consent
      ↓
runtime-altering env sanitization
      ↓
workspace + symlink boundary
      ↓
system config ownership / permission validation
      ↓
local command & file execution
```

这里的重要点在于，Agent 的本地权限边界不能只依赖 tool approval。extension 可以通过环境变量改变 executable lookup、runtime loading 或网络行为；symlink 可以让看似位于 workspace 内的路径越出工作区；系统级配置如果 ownership / permission 不可靠，也会成为隐式注入面。

### Why it matters

Gemini CLI 最近的安全改动正在形成一条连续 trust chain：MCP identity 与 OAuth、extension loader、workspace trust、filesystem path、symlink、temporary directory、environment 和 system config 都被视为 Agent tool runtime 的组成部分。

这说明 Coding Agent 的 sandbox / permission model 正从“允许哪个命令或工具”扩展到“执行环境是如何构造出来的”。对可扩展 Harness 来说，extension 与配置本身也必须经过 provenance、ownership、path 和 mutation policy 校验。

**Worth reading:** 是，但当前属于 nightly。优先看 environment mutation consent、runtime env sanitization、symlink boundary 和 system config ownership checks。
