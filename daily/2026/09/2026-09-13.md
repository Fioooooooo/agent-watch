### 1. Gemini CLI 0.61 nightly：把 Prompt Injection 防护推进到跨工具因果链，并进一步隔离 sandbox 运行状态

- **来源：** Google / Gemini CLI
- **发布时间：** 2026-09-12 01:25 UTC
- **主题：** Sandbox、Permissions、Prompt Injection、Agent Runtime、Coding Agent
- **优先级：** ★★★★★
- **状态：** Nightly / Pre-release
- **原文：** <https://github.com/google-gemini/gemini-cli/releases/tag/v0.61.0-nightly.20260912.g9c1b0a610>
- **相关 PR：** <https://github.com/google-gemini/gemini-cli/pull/29250>、<https://github.com/google-gemini/gemini-cli/pull/29214>

#### 发生了什么

Gemini CLI 的 9 月 12 日 nightly 只有两项主要变更，但都直接修改 Agent 的安全运行时：

1. 防止由构建文件修改和不可信参数触发的间接 Prompt Injection；
2. 强化 sandbox 文件系统边界，并把运行时状态从宿主机持久配置中隔离出来。

第一项改动不再只对单次 shell command 做静态危险性判断。Gemini CLI 开始扫描会话历史中的 `<untrusted_context>`，识别来自 Google Docs、Buganizer、WebFetch、MCP server response 等外部上下文提供的 token / 参数；当这些不可信内容进入 `shell`、`edit` 或 `write_file` 的执行路径时，策略层会要求显式用户确认。

同时，它开始追踪本轮会话中是否创建或修改过关键构建配置文件，例如：

- `package.json`
- `Makefile`
- `pyproject.toml`
- `BUILD.bazel`

一旦这些文件在会话中被修改，随后执行 `npm run`、`make`、`cargo`、`blaze` 等构建或测试命令时，会重新进入用户确认流程。对于非交互模式，相应策略会降级为 `ASK_USER` 或 `DENY`，而不是自动执行。

#### 技术细节

这一套机制可以抽象成：

```text
External / Untrusted Context
        ↓
  provenance tracking
        ↓
 shell flags / file edits
        ↓
 build-config mutation
        ↓
 later build / test command
        ↓
 runtime policy re-evaluation
        ↓
 explicit approval / deny
```

核心变化是权限判断开始跨越多个工具调用保存安全状态。构建配置文件的修改会影响之后命令的授权结果，因此工具调用不再是彼此独立的 permission check。

第二项 sandbox 改动则处理宿主机边界：

- sandbox runtime 不再直接依赖宿主机持久配置目录，而是使用清理后的配置和临时状态；
- 禁止把用户 home、文件系统根目录、`~/.gemini` 等敏感路径作为 sandbox 工作目录或挂载点；
- `trustedFolders.json`、`policy_integrity.json` 等安全策略状态被视为敏感文件，不暴露给 sandbox；
- 路径检查统一基于 realpath，并处理文件尚不存在、broken symlink、循环 symlink 等绕过场景；
- Docker、Podman、runsc、LXC 与 macOS Seatbelt 的工作目录和挂载规则使用更一致的敏感路径验证；
- runtime state 进一步迁移到受控的 ephemeral storage，减少 sandbox 内进程接触宿主机凭证和持久状态的机会。

#### 为什么重要

过去 Coding Agent 权限机制常以“某个命令是否危险”为中心，但 Prompt Injection 的真实攻击链通常跨越多个步骤：外部文本影响 Agent → Agent 修改配置 → 正常构建命令触发恶意副作用。如果每一步单独看都合理，单次工具级 allow / deny 无法覆盖这类攻击。

Gemini CLI 这次开始显式保存**不可信输入来源和构建文件修改状态**，再让后续工具调用继承这些安全信息。它与最近 Codex 的 authorization / provenance、GitHub Copilot 的 managed permissions，以及 Claude Code 对 resume 后权限一致性的持续加固，说明 Agent runtime 的权限模型正在从“工具白名单”向“带来源与历史状态的授权决策”扩展。

另一方面，sandbox 改动也说明隔离不只是禁止访问某些路径，而是要防止 Agent 在隔离环境中读到宿主机长期保存的信任决定、凭证和策略状态。真正的安全边界需要把**执行环境状态**本身也纳入隔离。
