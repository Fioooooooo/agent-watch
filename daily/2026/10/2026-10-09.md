### 1. Google AQuA：以部署版本为证据锚点的生产 Agent 质量闭环

**Source**：Google Developers Blog / ADK  
**Title**：The Outer Loop, Insights First: An Ambient Quality Agent That Diagnoses Your Production Agent  
**发布时间**：2026-10-08  
**Topics**：Evaluation、Agent Harness、Trace、Multi-agent、Recovery  
**Priority**：P1  
**Original**：[Google 官方工程文章](https://developers.googleblog.com/the-outer-loop-insights-first-an-ambient-quality-agent-that-diagnoses-your-production-agent/)

**What changed**

Google 公开 AQuA（Ambient Quality Agent）参考实现。它独立于在线请求路径运行，分析生产环境中的 Agent 执行轨迹，并将失败发现、聚类、复核、源码定位和回归验证连接起来。

**Technical details**

AQuA 每轮最多采样 1,000 个近期会话，根据 Agent 指令、工具定义及开发者目标进行评审，输出结构化的实际行为与预期行为差异。

相似问题首先形成候选聚类，再由独立模型读取完整轨迹进行复核。验证后的问题被记录为新增、反复出现或已解决状态，并关联部署时保存的不可变源码快照。

官方展示的多 Agent 旅行规划案例包含 32 次会话、1,583 个遥测跨度。初步识别出 42 条问题，聚合为 9 个候选问题组，经复核排除 3 组，最终保留 6 组有效问题。

典型问题包括未调用座位选择工具就保存用户指定座位、跨 Agent 委派时丢失饮食偏好，以及提示词要求使用工具但子 Agent 实际没有对应工具。

根因分析会引用部署源码中的具体文件和行号。修复两个问题并重新部署后，同一组测试的完整会话通过数从 5/32 增加至 13/32。

官方还讨论了生产轨迹抽样偏差、长会话压缩、模型评审误判，以及回放无法完整复原外部系统状态等限制。

**Why it matters**

对 Harness 质量治理而言，这种方案将失败关联到实际执行时生效的指令、工具定义、子 Agent 和源码版本，而不只是记录最终成功率。

真实生产故障还可以转化为可重复执行的回归测试，为后续 Harness 修改提供持续验证依据。

**是否值得阅读全文**：是

### 2. Codex 0.162.0：托管 Worktree、上下文能力与沙箱边界

**Source**：OpenAI / Codex  
**Title**：Codex 0.162.0  
**发布时间**：2026-10-08 18:55 UTC，北京时间 10 月 9 日 02:55  
**Topics**：Coding Agent、Workspace、Sandbox、Context Engineering、Tool Runtime  
**Priority**：P1  
**Original**：[Codex 0.162.0 Release](https://github.com/openai/codex/releases/tag/rust-v0.162.0)

**What changed**

该版本新增托管 Git worktree 创建和列举工具，支持自定义 Responses 兼容模型服务的远程上下文压缩与实时 Web 能力，并在 Code Mode 中加入可选的排序式工具检索。

**Technical details**

托管 worktree 工具以可信本地项目为执行前提，使并行任务的工作区管理进入 Agent 工具层。

自定义模型服务可以明确提供远程上下文压缩和实时 Web 能力，让 Harness 根据提供商实际能力配置运行方式。

安全相关修复包括 Linux 多拒绝路径的沙箱启动问题、拒绝可写的沙箱构造可执行文件、防止 ripgrep 配置削弱路径排除规则，以及 Windows 沙箱临时目录权限修复。

Responses 和 WebSocket 请求也开始遵循服务端返回的 `Retry-After` 建议进行重试。

**Why it matters**

这一版本将工作区隔离、工具发现、模型能力适配和操作系统级执行隔离放在同一个运行时演进过程中。

对于支持多任务、并行工作树和不同模型提供商的 Coding Agent，这些机制具有直接参考价值。

**是否值得阅读全文**：是

### 3. Claude Code 2.1.294–2.1.295：Hook 失败关闭与后台会话修复

**Source**：Anthropic / Claude Code  
**Title**：Claude Code v2.1.294、v2.1.295  
**发布时间**：2026-10-08  
**Topics**：Sandbox、Permissions、Hooks、MCP、Long-running Agent、Model Routing  
**Priority**：P1  
**Original**：[Claude Code 2.1.295 Release](https://github.com/anthropics/claude-code/releases/tag/v2.1.295)

**What changed**

命令和 HTTP Hook 新增 `onFailure: "block"` 配置。当 Hook 无法启动、超时或异常退出时，可以阻止对应动作继续执行。

相关更新还修复了插件热加载、守卫 Hook、后台子 Agent 恢复和 MCP 重新连接等问题。

**Technical details**

这一组版本进一步要求延迟注册的内置工具遵守 `--tools` 和 `--restricted` 限制。

插件重启或热加载期间，守卫 Hook 的竞争条件不再允许相关调用绕过检查。

后台会话和子 Agent 恢复逻辑得到改进，远程 MCP 在连接中断后能够使用退避策略重新连接，减少重复连接循环。

Gateway 增加上游模型白名单、首字节超时处理以及请求 ID 关联能力。

需要注意，`onFailure: "block"` 是可配置的失败关闭策略，并不代表所有 Hook 在失败时都会自动拒绝执行。

**Why it matters**

插件式 Harness 的权限机制不能假设 Hook 总能正常运行。启动失败、超时、异常退出和动态重载都需要明确的安全语义。

这些变更为 Agent 插件系统的故障关闭、权限继承和会话恢复提供了具体实现参考。

**是否值得阅读全文**：是

### 5. Vercel AI SDK 7.0.133–7.0.134：流式恢复保留工具调用事件

**Source**：Vercel / AI SDK  
**Title**：ai@7.0.133、ai@7.0.134  
**发布时间**：2026-10-08  
**Topics**：Streaming、Tool Use、Persistence、Agent State  
**Priority**：P2  
**Original**：[AI SDK 7.0.134 Release](https://github.com/vercel/ai/releases/tag/ai@7.0.134)

**What changed**

版本修复了恢复流式会话时，由模型提供商实际执行的工具调用丢失的问题。

同时，因工具更新触发的异步自动发送判断如果失败，现在能够正确向上传播错误。

前一版本还扩展了实验性决策状态的数据结构，使其能够包含有序文本、文件和 JSON 片段。

**Technical details**

由模型提供商执行的工具调用，与应用程序自身执行的工具调用具有不同的状态来源。

恢复流式会话时，如果只重建文本和应用侧工具结果，就会遗漏提供商执行过的工具事件，导致恢复后的状态与实际执行过程不一致。

异步自动发送条件的失败传播，则保证后续模型调用不会在调用方不知情的情况下继续使用不完整状态。

当前多段决策状态仍属于实验能力，部分模型适配器对文件片段存在限制。

**Why it matters**

长时间运行的 Agent 需要保存完整执行轨迹，而不仅是最终聊天文本。

当工具执行可能发生在不同层级时，流式恢复机制必须明确每类工具事件的来源及生命周期。

**是否值得阅读全文**：持续观察

### 7. GPT-6.1 Sol：Responses API 新增 Ultrafast 服务层级

**Source**：OpenAI / API Release Notes  
**Title**：Ultrafast mode for GPT-6.1 Sol  
**发布时间**：2026-10-08  
**Topics**：Model Serving、Latency、Agent Loop、API  
**Priority**：P2  
**Original**：[OpenAI 官方 Release Notes](https://openai.com/products/release-notes/)

**What changed**

Responses API 新增 GPT-6.1 Sol 的 Ultrafast 服务层级。

使用 `gpt-6.1-sol` 并配置 `service_tier: "ultrafast"`，可以降低生成输出 Token 之间的延迟。

**Technical details**

这一能力不需要切换模型名称，而是通过服务层级选择不同推理策略。

官方说明该功能面向 API 用户开放，受相应速率限制约束，并提供全球处理及美国、欧盟数据驻留支持。

目前公开说明未提供所有负载下统一的性能提升幅度。

**Why it matters**

对于包含多轮推理、工具调用和用户反馈的 Agent，模型输出延迟是整体执行时间的一部分。

新的服务层级为 Harness 提供了额外的模型路由与延迟预算选项，但端到端收益仍需结合实际 Agent 任务测量。
